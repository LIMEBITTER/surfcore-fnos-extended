# 2026-11-02 聊天时间说错（23:11 说成“还有六分钟到十一点半”）

## 现象

- 会话注入时间：`2026/11/2 23:11:32（Asia/Shanghai）`；
- 回复里出现：`还有六分钟就十一点半了，老大早点躺下吧`；
- 实际距 23:30 是 **18 分 28 秒**，不是 6 分钟。

## 根因

1. 时钟只在 prompt **最前面**注入；时间每轮变化，会破坏长 prompt 的前缀缓存，且离生成远；
2. 模型被要求像熟人聊天，容易自由发挥倒计时，但没做减法；
3. 服务端没有出口校验，错的“分钟数”直接发给用户。

## 方案（省 token + 高可用）

1. **时钟移到 prompt 末尾**，只保留一行：
   `【钟】2026-11-02 23:11:32 周一（Asia/Shanghai）`
2. 只有用户消息包含“几点/多久/还有/睡/今天/明天/昨晚/分钟”等意图时，才追加：
   - `【锚点】23:30 还有 18 分 28 秒；00:00 还有 48 分 28 秒`
   - 一句“算不出就写快 X 了，不要编分钟数”的写前检查
3. **发送前 `time-guard`**（零模型调用、零网络）：
   - 识别“还有 X 分钟就[到] H 点半/HH:MM”“现在/已经 HH:MM”；
   - 用服务器时间重算，错了就地改写分钟数/时间；
   - 历史/计划/引用句（昨晚、明天、约好…）跳过；
   - 解析失败 fail-open，绝不阻断发送；
   - 记录 `[time-guard]` 日志。
4. 不新增时间工具、不二次调用模型、不自动重试——这些都会增加 token/延迟。

## 验证

- 固定时钟 `2026-11-02T23:11:32+08:00`：
  - `还有六分钟就十一点半了` → `还有18分钟就十一点半了`
  - `还有六分钟就十二点` → `还有48分钟就十二点`
  - `现在 23:24` → `现在 23:11`
  - `昨晚还有六分钟就十一点半了` → 不改
  - `还有六分钟下班` / `我去睡了` → 不改
- 新测试：`scripts/test-time-context.mjs`；
- `test:audit` 110/110（新增一项）。

## 成本/高可用

- 普通消息只多一行约 10–20 token；有“时间意图”时再多一行锚点/规则；
- 时钟在末尾，保护前面静态 prompt 的缓存前缀；
- 校验纯本地、无网络、无模型调用；异常 fail-open；
- 时区固定 `Asia/Shanghai`，不依赖宿主环境。
